📘 Chunk 1: System Overview
The PKM-based ITS (Personal Knowledge Management–integrated Intelligent Tutoring System) developed by Dhamm.AI is a next-generation, adaptive learning ecosystem that connects personal learning data with intelligent tutoring capabilities.
 It combines:
PKM (Personal Knowledge Management) to organize learner inputs like notes, lectures, and resources into a connected graph.

Deep Knowledge Tracing (DKT) and Bayesian Knowledge Graph (BNKG) for mastery prediction and probabilistic concept relationships.

Hybrid KG-RAG retrieval for grounded, source-backed answers.

LLM Tutor + Action Layer to deliver personalized guidance, nudges, and interventions.

Its goal: make learning visible, explainable, personalized, and measurable.

🧩 Chunk 2: Key Design Objectives
Grounded Intelligence: Every AI-generated response cites real sources and graph paths.

Personalization by Evidence: Combines DKT predictions with Bayesian priors and memory models.

Privacy-Aware Architecture: Local inference options, tenant isolation, and PII redaction.

Adaptive Tutoring: Learners get feedback, tasks, and review schedules based on mastery evidence.

Cost-Aware Scaling: Routes tasks to optimal model based on latency and sensitivity.


🏗️ Chunk 3: Layered Architecture
The architecture consists of 6 layers:
Experience Layer:

Tutor chat UI (streamed answers, citations).

PKM Canvas for note editing and linking (Cytoscape visualization).

Dashboards for Bloom progression, mastery heatmaps, and cohort analytics.

Orchestration Layer (FastAPI):

Tutor Orchestrator assembles prompts and manages session state.

Model Router selects models based on privacy, latency, and cost.

MCP Tool Gateway handles typed tool calls (SQL, Graph, Vector, Python).

Knowledge Layer:

BNKG in Neo4j for concept maps and Bloom tags.

Vector retrieval in Milvus for semantic chunking.

Hybrid KG-RAG combines both for grounded retrieval.

Learning Models Layer:

DKT (PyTorch) for mastery prediction.

Memory Service for retention decay and spaced repetition.

Policy Engine for hinting, pacing, and task difficulty.

Data Layer:

PKM ingestion (files, notes, OCR, ASR).

ETL pipelines for event → feature transformation.

Storage in PostgreSQL + MinIO/S3 + Redis.

Ops Layer:

Observability via OTLP exporters and n8n automations.

Automated reindexing, retraining, and backup routines.


🧮 Chunk 4: Data Flow Summary
User interacts via Tutor UI or PKM Canvas.

Orchestrator gathers context and sends prompt to Model Router.

Router picks LLM (local Zamba/Ollama or cloud Claude/Kimi).

Tutor can call tools via MCP Gateway → Neo4j (BNKG), Milvus (semantic), or Python Sandbox.

PKM Ingest pipelines process new notes/files and update embeddings + BNKG.

Events (answers, quizzes) feed DKT + Memory → update BNKG → inform Policy Engine.

Action Layer generates interventions (tasks, reminders, feedback).

Teacher dashboard receives escalations via HITL.


📈 Chunk 5: Learning Models & Intelligence
🔹 DKT Service
Predicts mastery probability per concept from past interactions.
🔹 Memory Service
Models retention decay over time and triggers spaced repetition.
🔹 BNKG (Bayesian Knowledge Graph)
Represents concepts as nodes with probabilities and relationships.
🔹 BiDKT Variants
Bayesian-Integrated DKT: Online updates with CPT refresh.

Bidirectional DKT: Offline analytics with past-future context.

🔹 Policy Engine
Combines DKT + BNKG + memory scores to personalize pacing and difficulty.

🎯 Chunk 6: Action Layer (Decision → Intervention → Outcome)
Planner: Scores possible actions based on knowledge gap, forget risk, and pedagogical value.

Bandit Sequencer: Chooses best intervention (review, quiz, explanation, etc.).

Scheduler: Delivers in-app or via email/Matrix at optimized times.

Teacher Escalation: Routes difficult cases for human feedback (HITL).

Compliance & Audit: Tracks every action-outcome pair for reinforcement learning.

ITS · PKM · DKT — Final Architecture  1. Purpose:  Define a production-grade, privacy-aware, and scalable architecture for a Personal-Knowledge-Management-integrated Intelligent Tutoring System (ITS) with Deep Knowledge Tracing (DKT), hybrid KG-RAG retrieval, tool-using LLM tutor, long-term memory, and full observability.  2. Design Objectives • Grounded intelligence: Every tutor answer is backed by sources (notes/textbooks) and concept graph paths. • Personalization by evidence: Fuse DKT, LSTM memory/retention, and Bayesian Knowledge Graph (BNKG). • Agentic reasoning, safely: LLM can use tools (SQL/Neo4j/Vector/Python) through a secure gateway. • Cloud-scale + cost-aware: Autoscale microservices; route to the cheapest viable model per task SLA. • Security by default: Tenant/course/user isolation, PII redaction before cloud, audit trails.  3. Layered Architecture 3.1 Experience Layer • Tutor Chat UI: Streaming responses, citations panel, step-trace view, tool-use badges. • PKM Canvas: Note editor, link graph (Cytoscape), concept tagging, mastery overlay. • Dashboards: Bloom progression, mastery heatmaps, review schedule, cohort analytics. 3.2 Orchestration & Reasoning Layer • Tutor Orchestrator (FastAPI): Prompt assembler (state + context + policy), session/state, WS streaming. • Model Router: Policy-based selection (privacy, cost, latency, difficulty) → Cloud (Claude/Kimi-K2) or Local (Zamba/Ollama). • MCP Tool Gateway: Typed tools: sql.query, graph.query, vector.search, python.exec (sandboxed). 
• Trace Store: Compressed reasoning summaries + tool I/O + citations for audit/explainability. 3.3 Knowledge & Retrieval Layer • BNKG (Neo4j): Concepts, prerequisites, Bloom tags; CPT params; mastery properties. • Vector Retrieval: Nomic embeddings → Milvus; metadata filters (tenant/course/user/topic). • Hybrid KG-RAG (LlamaIndex): Graph paths + vector chunks merged with provenance for the LLM. 3.4 Learning Models Layer • DKT Service: Predict per-concept mastery from interaction sequences. • Memory Service: Retention/decay scoring; spaced-repetition recommendations. • Policy Engine: Difficulty/pace/hinting decisions from DKT + Memory + BNKG. • BiDKT Variants: o Bayesian-Integrated DKT (BiDKT, default online): Use DKT as an emission model (Pr(correct | state, item)) calibrated via Platt/Isotonic; combine with BNKG priors and prerequisite constraints. Inference: online filtering with Bayesian update; Training: periodic EM-style CPT refresh using logged sequences. Why: better interpretability and stability under sparse labels; propagates mastery to related concepts via graph. o Bidirectional DKT (BiLSTM-DKT, offline analytics): BiLSTM over full sequences to learn richer temporal features (uses past+future within a batch). Use: item difficulty calibration, cold-start parameterization, and hint policy tuning; not used for real-time since future tokens aren’t available. o APIs: /dkt/infer (online RNN), /bidkt/offline_train (batch), /bnkg/cpt_update (monthly EM). 3.5 Data & Ingestion Layer • PKM Ingest: Files/notes/links; optional Whisper ASR; OCR; metadata; PII redaction. • ETL/Feature Builder: Event → features (concept, Bloom, recency, correctness) for models. • Storage: PostgreSQL (events/users), MinIO (artifacts), Redis (hot cache), S3 lifecycle policies. 3.6 Platform & Ops Layer • Observability: OTLP exporters in every service; unified dashboards; golden-set eval runner. • Automation: n8n jobs — nightly re-index, weekly eval reports, monthly BN CPT recalibration, backup/restore tests. 
• Security: OIDC, RBAC/ABAC, secrets mgmt, WAF, egress control, data-at-rest encryption.  4. Data Flow (Text Diagram) User → Tutor UI ──

5. Component Blueprints & Rationale 5.1 FastAPI Gateway • Responsibilities: AuthN/Z, REST/WS APIs, request fan-out, response streaming, rate limits. • Why: Python ecosystem, async support, simple OpenAPI; pairs well with PyTorch, Neo4j drivers, LlamaIndex. 5.2 Tutor Orchestrator • Responsibilities: Prompt assembly (state + retrieved context + safety), tool policy, retries, response collation. • Why: Keeps LLM prompts lean, consistent; enforces tool-use rules; central place for pedagogy policies. 5.3 Model Router • Responsibilities: Route per policy (data sensitivity, latency, difficulty, cost); caching; fallbacks. • Why: Cut token spend, respect privacy; use strong MoE (Kimi/Claude) only when needed; local Zamba for drafts. 5.4 MCP Tool Gateway • Responsibilities: Safe, typed access to sql, graph, vector, python. • Why: Extensible, standard interface; auditable tool calls; easy to add calculators/simulators later. 5.5 BNKG (Neo4j + pgmpy) • Responsibilities: Concept graph with Bloom tags; CPT updates; mastery overlays. • Why: Explainable pathways and prerequisite logic; Bayesian smoothing of noisy evidence. 5.6 Vector Retrieval (Nomic + Milvus + LlamaIndex) • Responsibilities: Semantic memory of notes/content; hybrid graph+vector queries with provenance. • Why: Grounded answers, personal notes reuse, low hallucination; Milvus gives prod-grade scale & speed. 5.7 DKT & Memory Services (PyTorch) • Responsibilities: Mastery probabilities (DKT), retention/decay (LSTM); export signals to Policy. • Why: Evidence-based personalization; schedule spaced reviews; accelerate weak-topic recovery. 
5.8 Long-term App Memory (Mem0) • Responsibilities: Persist learner/tutor facts (preferences, pitfalls, goals); TTL/policy. • Why: Reduce prompt size; continuity across weeks; deeper personalization. 5.9 Storage & Streams • PostgreSQL: Events, users, attempts; ACID. • MinIO/S3: Artifacts (docs/audio/models) with lifecycle. • Redis/Kafka: Caching + event pipelines; bursts smoothing. 5.10 Observability (OTLP) & n8n • Responsibilities: Metrics/traces/logs, eval pipelines, drift alerts; automation for re-index/retrain/report. • Why: Predictable SLOs, lower MTTR, self-healing. 5.11 Security & Privacy • Responsibilities: OIDC SSO, RBAC/ABAC, PII redaction, KMS encryption, WAF, audit trails, isolation. • Why: Educational PII compliance, safe tool-use, tenant boundaries.  6. Deployment Topology Deployment Topology • Kubernetes: namespaces by env (dev/stage/prod); HPA autoscaling; PodSecurity; NetworkPolicies. • Data plane: Private subnets (Neo4j, Milvus, Postgres); Bastion for admin; WAF at edge; API Gateway/CDN. • Models: GPU node pool for LLM/DKT; local Ollama runners for Zamba; cloud APIs for Claude/Kimi via VPC egress. • CI/CD: GitHub Actions → Docker build → Helm deploy; Blue-Green/Canary; SAST/DAST; SBOM, image signing. • Backups/DR: Snapshots for Postgres/Neo4j/Milvus; MinIO versioning; restore drills.  9. Observability & Quality Gates • Metrics: grounding rate, citation coverage, tool-use %, hallucination flags, p95 latency, tokens/cost. • Evals: golden questions per course; rubric scoring; monthly BN CPT drift check. • Alerts: grounding < 80%, hallucination > 5%, cost budget breach, CPT instability, queue lag. • n8n automations: re-indexing, retraining, report mails, rollback triggers.  10. Security & Compliance • OIDC SSO; RBAC (role) + ABAC (tenant/course/user); signed MCP tool manifests. • Encryption in transit (TLS 1.2+) and at rest (KMS); key rotation. • PII redaction before cloud LLM; DLP checks; immutable audit logs; right-to-erasure workflows. 
 11. Success Metrics (Target) • Learning: +20–30% weekly mastery lift on weak nodes; −25% time-to-mastery. • Quality: ≥85% grounded answers; ≥70% tool-verified math/logic; <5% hallucination flags. • Action Layer: ≥12–20% uplift vs. control on action CTR → completion; positive off-policy estimated reward; review adherence >85%; escalation latency < 10 min. • Ops/Cost: p95 tutor < 4s (warm cache); −20% token cost via router; MTTR < 15 min. 12. Risks & Mitigations • Model sprawl / cost creep → Router policies, budget alerts, golden evals. • Graph drift / CPT instability → Shadow runs + eval gate before promotion. • Privacy lapses → Default local inference for sensitive flows; strict egress; audit. • Content variance → Teacher review queue; rubric eval; provenance required.  13. Glossary (Quick) • BNKG: Bayesian Knowledge Graph (concept graph + probabilistic inference). • DKT: Deep Knowledge Tracing (LSTM predicting concept mastery). • KG-RAG: Hybrid retrieval that merges graph paths and vector similarity. • MCP: Model Context Protocol (standardized tool interface for LLMs). • Mem0: Long-term app memory store for LLM agents.  14. Action Layer (Decision → Intervention → Outcome)  Purpose: Convert predictions into measurable interventions. Components - Action Planner: Priority score P = w1·(knowledge_gap) + w2·(forget_risk) + w3·(pedagogical_value) − w4·(novelty_penalty) − w5·(cost); safety caps (daily limits, fatigue). - Bandit Sequencer: Contextual Thompson/LinUCB to pick among actions (review, practice, explanation, quiz, concept-map task, peer Q, escalate-to-teacher). Counterfactual logging for off-policy evaluation. - Scheduler & Delivery: Immediate (in-session) or scheduled via n8n; channels: in-app, email, Matrix; quiet-hours, batching. - HITL: Teacher review queue for escalations; acceptance/rejection logged to retrain policy. - Compliance & Guardrails: fairness constraints (per-cohort exposure), explanation requirement, audit trails. 
Data Contracts - action_exposure{action_id, user, time, channel, props} - action_outcome{action_id, user, time, clicked?, completed?, mastery_delta} Why it helps: Turns insights into consistent, accountable action—closing the loop between analytics and learner outcomes while enabling A/B tests and continuous improvement.
